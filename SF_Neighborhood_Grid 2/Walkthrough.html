01 / DATA FOUNDATION

Dataset & Processing Details

The project uses your supplied Film Locations in San Francisco CSV. We now group records by Analysis Neighborhood instead of Supervisor District, so recognizable places such as Chinatown, Marina and North Beach become the comparison units.

2,214TOTAL LOCATION RECORDS
2,070MAPPED RECORDS
41ANALYSIS AREAS DISPLAYED
40AREAS WITH RECORDS

Mapped records contain 290 distinct title and release-year combinations. A record is one filming-location entry, not a unique film or unique address. The same title can appear in several rows because it has several recorded locations.

Data pipeline details

  • Cleaning: trim neighborhood names and year text, while preserving the source title, location and other fields.
  • Filtering: match the supplied neighborhood names to the layout. All 40 named neighborhoods match. The 144 rows with no neighborhood are excluded from mapped views and reported; missing names are not guessed from coordinates.
  • Aggregation: group matching records by neighborhood and count the rows in each group. Count distinct title/year combinations separately.
  • Retaining zero values: DataSF supplies 41 analysis areas. Visitacion Valley has no records in this CSV, so it is still displayed as a gray tile with zero. A zero means no matching records in this dataset, not that filming never happened there.

02 / STEP BY STEP IMPLEMENTATION

How the Cartogram is Built

D3 connects data to page elements. We design the geographic abstraction, the visual encoding and the interactions. HTML provides the structure, CSS controls appearance, and SVG holds the squares, labels and map paths.

Read CSV and local geography→Filter and count→Bind and draw→Respond to interaction

Step 1: Define the Neighborhood Grid Layout

The earlier version used eleven supervisor districts. This version uses 41 DataSF analysis areas so the map offers finer spatial detail and recognizable neighborhood names.

The layout is precomputed using the analysis-area geometry. A connected set of 40 mainland grid cells approximates the city footprint. Geographic representative points are assigned one-to-one to cells by minimizing overall displacement. Treasure Island occupies a detached northeast inset. Its displayed distance is not geographically accurate.

At runtime, D3 reads the saved layout. Each neighborhood has a name, a column, a row and short label lines. The row and column place the tile; the CSV’s individual filming coordinates do not directly place that tile.

Find this responsibility in the project: data/neighborhood-layout.json stores the layout; neighborhoods holds it after loading. The map’s row and column calculations use those values. The browser is not solving the layout optimization on every page load.

Concept example — shortened for explanation; surrounding variables come from your implementation.

const layout = await d3.json(
  "data/neighborhood-layout.json"
);
const neighborhoods = layout.neighborhoods;

// Each area already has a saved column and row.
// Convert its grid position into screen coordinates.
const x = d.col * cellStep;
const y = d.row * cellStep;

Step 2: Render Tiles with a D3 Data Join

After filtering, the page attaches a count to each neighborhood object. A keyed data join matches that object to its SVG group using the neighborhood name. Each group contains a square, a name and a count. The name acts as a stable identity even when its count changes.

Every square has the same dimensions. The group’s position is calculated from its row and column. A neighborhood with no matching records stays in the layout with a zero rather than disappearing.

Look for: drawMap, data, join, the name key, and the group-position calculation. These are search terms for understanding your own implementation, not replacement instructions.

Concept example — shortened for explanation; surrounding variables come from your implementation.

const tiles = grid.selectAll("g.tile")
  .data(neighborhoodData, d => d.name)
  .join("g")
  .attr("class", "tile")
  .attr("transform", d =>
    `translate(${d.col * cellStep}, ${d.row * cellStep})`
  );

// Each group contains a square, a name and a count.
// Keep the same name key when filtered counts change.

Step 3: Create the Color Scale and Legend

A sequential square-root scale turns counts into colors. It makes smaller counts more distinguishable. The input range is fixed from zero to the full dataset’s largest neighborhood total, 299 records, in Financial District/South Beach. This keeps a given color numerically consistent across filters.

The legend samples the same scale used by both maps. Gray is a separate zero-count color. All tiles are equal in size; their area does not represent record count, land area or population.

Look for: state.color, scaleSequentialSqrt, the input domain, the rectangle’s fill, and legend. Color is a data encoding, so changing the page background alone does not change it.

Concept example — shortened for explanation; surrounding variables come from your implementation.

const color = d3.scaleSequentialSqrt(palette)
  .domain([0, 299]);

// Apply the count-to-color rule to each tile.
tiles.select("rect")
  .attr("fill", d => d.count === 0
    ? zeroColor
    : color(d.count));

// The legend and geographic reference share this scale.

Step 4: Connect Interaction and Geographic Reference

The reference map reads local GeoJSON boundaries. D3 projects those shapes and draws their SVG paths. It provides geographic context for the simplified grid; it is not a second ranking chart.

Both maps use the same counts and selection state. Selecting North Beach in either view highlights the corresponding area in the other and updates the archive. Hovering or focusing an area also helps locate it in both views. Enter and Space select a focused area; Escape clears the selection.

Look for: drawReference, geoMercator, geoPath, events, choose, and updateSelection. Shared state links the views without changing the underlying records.

Concept example — shortened for explanation; surrounding variables come from your implementation.

const projection = d3.geoMercator()
  .fitSize([width, height], geography);
const path = d3.geoPath(projection);

// Both views select a neighborhood using the same name.
tiles.on("click", (event, d) => choose(d.name));

// choose updates the shared selection, highlights
// both maps and refreshes the neighborhood record list.
A geographic approximation: these are DataSF analysis areas based on grouped census tracts, not legally defined neighborhood boundaries. Equal tiles simplify shape, distance and some adjacencies. The reference map makes that simplification visible.

TASK 01 / COLOR ENCODING

Change the Color Palette

Step 1: Locate the Existing Color Scale

In cartogram.js, find state.color inside the data-loading code. This is the current palette:

state.color = d3
  .scaleSequentialSqrt(d3.interpolateRgb("#e5eed5", "#efacd5"))

Step 2: Replace the Palette

state.color = d3

Step 3: Read the Current Neighborhood Data

In cartogram.js, keep one tooltip selection near the top of the file. Add or update showInfo using the neighborhood name, count and filtered total. This function also preserves the linked-map hover highlight.

const tooltip = d3.select("#tooltip");

function showInfo(event, d) {
  state.hovered = d.name;
  d3.selectAll(".tile,.geo-neighborhood").classed(
    "hovered",
    (item) => item.name === d.name,
  );
  const share = state.filtered.length
    ? d3.format(".1%")(d.count / state.filtered.length)
    : "0%";
  tooltip
    .attr("hidden", null)
    .text(
      `${d.name} · ${fmt.format(d.count)} records · ${share} of filtered mapped records`,
    );
  const rect = event.currentTarget.getBoundingClientRect();
  positionTooltip(
    Number.isFinite(event.clientX)
      ? event
      : {
          clientX: rect.left + rect.width / 2,
          clientY: rect.top + rect.height / 2,
        },
  );
  updateReferenceCaption();
}

Step 4: Position and Hide the Tooltip

Add or update these helpers in cartogram.js. Positioning is clamped to the viewport; clearing hover hides the panel and updates the linked reference. The existing render function already calls clearHover() after filters change.

function positionTooltip(e) {
  const box = tooltip.node().getBoundingClientRect();
  tooltip
    .style(
      "left",
      `${Math.max(8, Math.min(e.clientX + 14, innerWidth - box.width - 8))}px`,
    )
    .style(
      "top",
      `${Math.max(8, Math.min(e.clientY + 16, innerHeight - box.height - 8))}px`,
    );
}

function clearHover() {
  state.hovered = null;
  tooltip.attr("hidden", true);
  d3.selectAll(".tile,.geo-neighborhood").classed("hovered", false);
  if ($("reference-caption")) updateReferenceCaption();
}

Step 5: Bind Pointer and Keyboard Events

Update the existing events(selection) function. Keep click selection and keyboard controls while adding tooltip handlers. The project already calls events(tiles) when drawing tiles, and attaches the same behavior to the geographic reference.

function events(selection) {
  selection
    .attr("tabindex", 0)
    .attr("role", "button")
    .attr(
      "aria-label",
      (d) => `${d.name}: ${d.count} location records. Select to view records.`,
    )
    .on("click", (e, d) => choose(d.name))
    .on("keydown", (e, d) => {
      if (e.key === "Enter" || e.key === " ") {
        e.preventDefault();
        choose(d.name);
      }
    })
    .on("pointerenter", showInfo)
    .on("pointermove", positionTooltip)
    .on("pointerleave", clearHover)
    .on("focus", showInfo)
    .on("blur", clearHover);
}
